## 1. Purpose

Build the secure server-side foundation behind the founder-approved Remodel Studio customer journey without placing secrets, customer photos, or customer PII in GitHub Pages or the public repository.

Controlling flow:

**Space Truth Intake → Preserve / Change / Must-Have → Planning Budget / Timing / Property Context → Secure Customer Photo Intake → AI Concept Visualization → Customer Selection → Human Buildability Review → Precision Scope Map → Pre-Estimate Intelligence Packet → Shell & Co Lead Routing → Site Visit / Estimate**

## 2. Architecture Selected

**SELECTED:** Supabase for the first production-capable backend architecture.

Components:

- Supabase Auth — anonymous authenticated project session for low-friction customer ownership during the Remodel Studio flow;
- Supabase Postgres — project, asset, concept, review, rate-limit and audit provenance records;
- Row Level Security — customer session may read only records owned by its `auth.uid()`; write-sensitive operations remain server-side;
- Supabase Storage — private source and result buckets;
- Supabase Edge Functions — request validation, signed upload issuance, upload finalization, OpenAI orchestration, result retrieval and deletion;
- OpenAI Image API — server-side only;
- GitHub Pages — public frontend only; never receives a secret key.

### Why Supabase

For Shell & Co's first secure implementation, Supabase provides the strongest combined fit across private storage, expiring signed access, relational provenance, RLS, serverless functions, authentication, deletion workflows and founder manageability in one control plane.

### Alternatives Evaluated

**Cloudflare Workers + R2 + D1:** strong raw infrastructure economics and private object support, but requires more custom authentication/authorization policy glue for this project. Retain as a future scale/cost alternative, not the BR02 default.

**Firebase Auth + Storage + Firestore + Functions:** mature security rules and ecosystem, but splits the governed workflow across more products and requires paid billing for Cloud Functions. Not selected for the initial Shell & Co proof.

## 4. Security Boundary

Controlling production path:

`GitHub Pages → Supabase Auth session → Edge Function → private Postgres/Storage → OpenAI API → private result Storage/Postgres → authorized signed result → GitHub Pages`

Rules:

1. OpenAI secret exists only in backend secret storage.
2. Supabase service-role key exists only in Edge Function runtime secrets.
3. Browser receives only publishable client configuration and short-lived signed object access where required.
4. Source and generated images are never placed in public buckets.
5. No customer image is committed to GitHub.
6. No customer name, email, phone, address or exact location is used in the BR02 proof.
7. All write-sensitive database actions use Edge Functions/service authorization.
8. Anonymous customer sessions are authenticated and isolated by `auth.uid()` + RLS.
9. Production anonymous-auth activation must add CAPTCHA/Turnstile abuse protection.

## 5. Private Storage Architecture

Private buckets:

- `remodel-source-private`
- `remodel-results-private`

Proof upload limits:

- allowed types: JPEG, PNG, WEBP;
- maximum file size: **6 MiB** for the initial standard-upload proof;
- path pattern: `{auth.uid()}/{project_id}/{kind}/{asset_id}.{ext}`;
- signed upload is issued only after ownership and declared type/size validation;
- signed upload path is unique and must not overwrite an existing object;
- upload finalization re-reads the actual stored object and validates byte size and file signature/magic bytes;
- SHA-256 is computed after upload and stored as provenance;
- failed validation causes object deletion and a rejected asset record;
- generated result retrieval uses a short-lived signed URL, default **60 seconds**;
- no public object URLs are authorized.

Production files above 6 MiB require a separately tested resumable/TUS upload path before the public 10 MiB UX limit is activated.

## 6. Project Data Model

### `remodel_projects`

Stores anonymous owner ID, project type, planning budget, timing, property context, Space Truth, Preserve/Change/Must-Have, design direction, written vision, accessibility requirements, workflow status, preferred concept ID and retention timestamp.

### `remodel_assets`

Stores source/result asset provenance: owner, project, private bucket/path, kind, MIME type, actual byte size, SHA-256 and validation state.

### `remodel_concepts`

Stores concept ID, project/source linkage, ordinal 1–4, design direction, model, quality, size, prompt compiler version/hash, OpenAI request ID, generation status, result asset and normalized error code. **Raw compiled prompts are not stored.**

### `buildability_reviews`

Stores GREEN/YELLOW/RED status and reviewer notes. Customer sessions may read their project's review but may not create or modify a controlling review.

### `generation_events`

Stores non-PII quota/cost-control events. Raw IP addresses are prohibited; only an HMAC/SHA-derived IP hash may be stored when rate limiting requires it.

### `audit_events`

Stores minimal non-PII lifecycle provenance, including deletion tombstones. No customer image, customer contact information or raw prompt text is authorized in audit records.

## 7. OpenAI Model / API Decision

**Use:** transform the customer/test source photo into a controlled remodel concept while preserving source-space facts where not authorized to change.

High-quality generation is reserved for a later founder-authorized final-render tier after proof cost/quality is measured.

## 10. Privacy / Retention Architecture

Default pre-estimate retention for source photos, generated concepts and associated project content: **30 days from project creation/last governed activity**, unless the customer converts to a signed project and a later adopted project-record policy applies.

Customer rights/control:

- request deletion before expiry;
- deletion removes private source/result objects and associated active project rows;
- minimal non-PII deletion/audit tombstone may remain for up to **12 months** for system integrity, abuse/security and operational audit;
- photos are not automatically licensed for Shell & Co marketing use;
- marketing/photo-marketing permission requires a separate affirmative authorization.

Production disclosure must explain in plain language:

1. why the image is collected;
2. that it may be transmitted to OpenAI for the requested visualization;
3. that Shell & Co stores project content in a private backend rather than the public GitHub repository;
4. the default retention period;
5. how deletion may be requested;
6. that generated imagery is conceptual;
7. that estimate-contact consent is not marketing consent.

## 12. Error-State UX Contract

- `UPLOAD_NOT_READY`
- `GENERATION_DISABLED`

- `BUDGET_LIMIT_REACHED`
- `MODERATION_BLOCKED`
- `GENERATION_TIMEOUT`

Never send provider secrets, stack traces, raw upstream responses or internal storage paths to the public UI.
